# DSH–Codex 会话维护系统设计规格

- 日期：2026-08-26
- 状态：已确认，进入实施计划
- 目标系统：`dsh-session-maintenance`
- 交付形态：全新独立项目

## 1. 决策摘要

`dsh-session-maintenance` 是全新构建的独立会话维护系统，不以 `dsh-codex-session-sync` 为兼容底座，也不依附 EAC、Maintenance 服务或 DSH 进程存活。它以本地维护引擎为唯一业务核心，对 DSH 和 Codex 分别使用版本化适配器，并向 DSH 插件、独立看板和 Codex 插件提供同一套能力。

系统维护的是“同一逻辑会话在不同平台上的版本图”，而不是简单复制文件。每次观察到有效内容变化都会建立不可变版本；安全的前缀增长可以自动快进，双方各自继续造成的分叉必须保留为两个分支，并由用户决定如何合并或继续。

DSH 向 Codex 的迁移有两种明确不同的模式：

1. **创建 Codex 延续任务（默认）**：通过 Codex 支持的任务创建入口建立新的原生 Codex 任务，把选定 DSH 版本作为带来源标识的上下文交给新任务。此模式不改写 Codex 历史数据库。
2. **原生双向镜像（按会话白名单启用）**：让少数重要会话在 DSH 与 Codex 中保持原生历史映射。此模式需要版本锁定的 Codex 原生存储适配器、停写窗口、完整事务备份和回滚；任何格式不兼容都会暂停镜像，绝不猜测写入。

新系统稳定并接管业务后，旧 `dsh-codex-session-sync` 插件、`/codex-sync` 命令、旧管理页按钮和旧 ledger 全部退出运行环境。新项目不承担旧插件 API、命令、配置或账本兼容；旧代码只作为已经验证过的行为样本，帮助建立新系统测试用例。

## 2. 目标

### 2.1 核心目标

- 为 Codex 与 DSH 会话建立稳定的一对一或一对多逻辑映射，避免重复导入。
- 为每个逻辑会话保存可追溯的版本、父子关系、平台分支和人工标签。
- 支持 Codex → DSH 的安全增量同步。
- 支持 DSH → Codex 的默认“新建可持续任务”。
- 为明确选中的重要会话提供受控的原生双向镜像。
- 在 DSH 中提供会话右键操作，在独立看板中提供完整图形化维护，在 Codex 中提供工具卡片或 Skill 入口。
- 所有写入都经过扫描、计划、确认、事务执行、验证和失败恢复。
- DSH、Codex 或界面插件升级后，能够明确识别适配状态并阻止不安全写入。
- 保留现有同步器已经验证的 UUID、标题、分支、备份和幂等行为。

### 2.2 可迁移性目标

第一阶段以功能正确和本机稳定为首要目标，但数据模型和路径设计必须避免绑定当前 EAC、固定盘符或单一 DSH profile。迁移到另一台 Windows 机器时，应能够复制维护数据目录、重新登记 Codex home 与 DSH profile，然后重新扫描并恢复映射。

## 3. 非目标

- 不修改或注入 Codex Desktop 的原生侧边栏、右键菜单或内部 React 页面。
- 不依赖 EAC，不为 EAC 看门狗、私有目录或专有启动协议增加业务分支。
- 不在第一阶段实现实时逐 token 同步；同步以显式任务或受控计划任务为边界。
- 不把 Zstd 会话文件、SQLite 数据库或大段 JSONL 直接提交到 Git。
- 不自动拼接两条已经分叉的对话，不伪造工具调用或思维过程。
- 不自动传播删除操作。
- 不在 Codex 正在写入时强制关闭 Codex 或抢占其文件。
- 不把云同步、多人协同或跨设备冲突解决列入首版。

## 4. 历史基线与重建原因

历史上的 `dsh-codex-session-sync@0.3.3` 已验证以下业务行为可行：

- 按 Codex UUID 和标题建立映射；
- 使用来源 hash、修改时间和 DSH hash 跳过未变化会话；
- Codex 来源变化时重新转换会话，并保留 DSH 本地新 对话分支；
- 对重复或冗余分支进行有边界的整理；
- 写入前备份，并重建 DSH workspace/projection；
- 通过 `/codex-sync` 和 DSH 管理面板显式触发；
- 已与 EAC 解耦，只控制登记过的官方 DSH 进程。

这些行为转换为新项目的回归测试，不直接搬运旧运行链。旧插件仍然是单向、以整份会话重写为中心的同步器，只有一份平面 ledger，缺少独立版本图、通用冲突模型、反向适配器、原生 Codex 写入保护和完整 GUI。在它上面继续叠加双向写入既增加兼容分支，也妨碍数据模型和性能优化，因此新系统从干净架构重新实现。

## 5. 术语与不变量

### 5.1 术语

- **平台会话（Platform Session）**：Codex thread 或某个 DSH profile 中的 session。
- **逻辑会话（Logical Session）**：维护系统认为属于同一工作脉络的一组平台会话。
- **版本（Version）**：某一时刻会话规范化内容与可同步元数据的不可变快照。
- **平台引用（Platform Ref）**：指向某个平台会话当前已观察版本的可移动指针，例如 `codex/local/<thread-id>`。
- **规范引用（Canonical Ref）**：用户选定的逻辑会话主线，不代表强制覆盖任一平台。
- **快进（Fast-forward）**：目标版本是来源版本的祖先，能够只增加新内容而不改变既有内容。
- **分叉（Divergence）**：两个平台版本拥有共同祖先，但双方都出现独立内容或既有内容被编辑。
- **延续任务（Continuation）**：根据某个版本创建的新 Codex 原生任务；新任务从创建时起拥有独立历史。
- **原生镜像（Native Mirror）**：同一逻辑会话的 DSH 与 Codex 平台会话由系统持续维护映射和双向更新。
- **Checkpoint**：用户命名的恢复点，绑定版本图状态、平台引用和执行前备份索引。

### 5.2 系统不变量

1. 版本内容不可变；变化产生新版本，不修改旧版本。
2. 每个平台会话在同一逻辑会话中只有一个当前平台引用。
3. 所有实际写入必须对应一个持久化执行计划和事务记录。
4. 写入前必须重新核对来源与目标指纹，过期计划不得执行。
5. 自动合并只允许已证明安全的前缀增长或单边元数据变化。
6. 对话分叉不得静默丢弃、覆盖或按时间戳机械交错。
7. 删除永远需要用户明确确认，并且与“解除映射”是两个操作。
8. Codex 原生适配器不兼容时，所有依赖它的镜像立即暂停。
9. 无法等价表示的 DSH 工具事件必须降格为带来源标识的“DSH 导入记录”。
10. DSH、Dashboard 和 Codex 三个入口必须调用同一个引擎和同一个版本存储。

## 6. 总体架构

目标代码采用独立 monorepo `dsh-session-maintenance`：

```text
dsh-session-maintenance/
├─ apps/
│  ├─ engine/                         # 常驻本地服务、任务队列和 CLI
│  └─ dashboard/                      # 独立会话维护看板
├─ packages/
│  ├─ session-domain/                 # 规范化模型、版本图与合并规则
│  ├─ session-store/                  # SQLite、内容寻址对象和事务备份
│  ├─ adapter-dsh/                    # 官方 DSH profile 读写
│  ├─ adapter-codex-read/             # Codex 稳定只读扫描
│  ├─ adapter-codex-continuation/     # 通过受支持入口创建新 Codex 任务
│  ├─ adapter-codex-native/           # 版本锁定的实验性原生镜像写入
│  └─ local-api-client/               # DSH/Codex 入口共用的受限客户端
├─ plugins/
│  ├─ dsh-session-maintenance/        # DSH 会话右键菜单与参数/操作入口
│  └─ codex-session-maintenance/      # Codex Skill、MCP 工具及工具卡片
├─ fixtures/                          # 已脱敏的平台版本契约样本
└─ docs/
```

新项目不依赖或加载 `dsh-codex-session-sync`。其 DSH 插件、Codex 插件、引擎、看板和存储协议一起按新业务模型设计，避免为了旧命令或旧 ledger 引入双实现、转换层和启动开销。

### 6.1 依赖方向

```text
DSH 右键菜单 ─┐
独立 Dashboard ├─> 受限本地 API ─> Engine ─> Domain + Store ─> 平台适配器
Codex 工具卡片 ┘
```

界面不得直接读取或写入 Codex/DSH 数据文件，也不得各自实现冲突算法。平台路径、格式知识和写入事务只存在于适配器与 store 层。

Dashboard 在构建期使用与 DSH Maintenance 相同的 `@linmu/dsh-management-kit/client`、`--dsm-*` 设计变量和交互组件。该 UI 包固定版本并打入 Dashboard 产物，因此只共享视觉与组件契约，不让会话系统在运行时依赖 Maintenance 引擎或其状态目录。

## 7. 本地引擎与 API

引擎是独立于 DSH 和 Codex 的本机进程。关闭或重启 DSH 不会中断已经持久化的扫描结果、计划或恢复信息。

核心命令统一为四阶段：

```text
scan -> plan -> apply -> verify/restore
```

- `scan`：对平台执行只读发现；稳定读取后可把观察结果保存为不可变版本并移动对应的 observed platform ref，但不写平台、不移动 canonical ref，也不表示同步已经完成。
- `plan`：根据上次共同祖先、当前两端 head 和用户策略生成不可变计划。
- `apply`：重新校验计划指纹，建立事务备份，顺序执行计划。
- `verify`：重新读取目标平台，确认可发现、可解析、映射一致；失败则 `restore`。

每个计划包含：计划 ID、创建时间、逻辑会话、来源/目标版本、适配器版本、操作列表、风险级别、需确认项、前置指纹和计划 hash。`apply` 只接受未过期且 hash 完整的计划。

### 7.1 本机 API 安全边界

- 仅监听 `127.0.0.1`，不监听局域网地址。
- 首次安装生成随机 capability token，并以仅当前 Windows 用户可读的权限保存。
- 只允许已登记的 Codex home、DSH home 和 profile；API 参数不能提交任意文件路径。
- 删除、覆盖式解析、启用原生镜像和恢复操作需要一次性确认 nonce。
- 每个平台数据根目录使用独占写队列；不同逻辑会话可并行扫描，但不能并行写同一平台存储。
- 所有操作记录调用来源、计划 hash、适配器版本和结果，但日志不复制完整私密对话正文。

## 8. 版本存储模型

维护数据目录由 `SESSION_MAINTENANCE_HOME` 指定；未指定时使用当前 Windows 用户的本地应用数据目录。目录结构为：

```text
session-maintenance-home/
├─ config.yaml
├─ metadata.sqlite
├─ objects/sha256/<前两位>/<hash>.zst
├─ transactions/<transaction-id>/
│  ├─ plan.json
│  ├─ journal.jsonl
│  ├─ backups/
│  └─ verification.json
├─ adapter-state/
└─ logs/
```

SQLite 保存关系、索引和状态，内容寻址对象保存规范化会话正文。采用 Git 式有向无环图语义，但不使用 Git 直接存放平台数据库或压缩会话文件。

### 8.1 主要实体

**LogicalSession**

- 稳定 UUID；
- 展示标题；
- canonical ref；
- 同步模式：`continuation`、`native-mirror` 或 `paused`；
- 创建时间、归档状态和用户标签。

**PlatformBinding**

- 平台类型、实例/profile ID、平台 session ID；
- 当前平台 ref；
- 平台格式指纹和适配器版本；
- 上次成功同步的共同版本；
- 只读、可写、忙碌或不兼容状态。

**SessionVersion**

- 由规范化 manifest 与事件内容计算的内容 hash；
- 零个、一个或两个父版本；
- 规范化事件对象；
- 标题、归档等可同步元数据；
- 来源平台、来源 ID、采集时间和 provenance；
- 兼容性/降格报告。

**Checkpoint**

- 用户命名和说明；
- 一组逻辑会话 ref 与平台 ref；
- 相关事务备份索引；
- 创建者和创建时间。

### 8.2 规范化与 hash

规范化事件至少包含稳定事件 ID、角色、可展示正文、顺序、父子/分支关系、附件引用、工具事件表示和来源锚点。以下观察性字段不得影响内容 hash：扫描时间、本机绝对路径、临时端口、进程 ID、日志位置和仅由读取顺序产生的字段。

标题和归档状态分别参与元数据 hash；正文 hash 不因单纯重命名而变化。平台适配器必须提供稳定排序和字段白名单，未知字段保存在来源扩展区，但不会在未经适配的情况下写入另一平台。

### 8.3 版本与引用

- 每次发现正文或受管元数据发生变化，就创建一个新版本。
- 自动扫描只移动对应平台 ref，不自动移动 canonical ref。
- 自动安全快进完成后，canonical ref 可按该逻辑会话策略一起前进。
- 用户可为任何版本添加名称、说明和 checkpoint；这不会复制正文对象。
- 两父版本只由用户确认的冲突解析产生。

## 9. 扫描、差异与决策矩阵

扫描先读取轻量索引、大小、修改时间、事件数量和已知前缀摘要。只有候选发生变化时才读取并规范化完整正文。读取过程中若文件大小或修改时间改变，则本次结果标为 `UNSTABLE_READ`，稍后重试，不建立版本。

| 状态 | 判定 | 默认动作 |
| --- | --- | --- |
| 两端未变化 | 两端 head 均等于上次同步版本 | 跳过 |
| 仅来源前缀增长 | 目标是来源祖先，既有事件不变 | 生成安全快进计划 |
| 仅目标前缀增长 | 来源是目标祖先 | 更新目标平台 ref；按方向策略决定是否反向快进 |
| 仅一端标题变化 | 正文相同，另一端标题未变 | 在允许同步标题时自动传播 |
| 两端标题都变化 | 共同基线后双方均重命名 | 元数据冲突，人工选择 |
| 一端归档变化 | 原生镜像已启用 | 自动同步归档状态 |
| 一端删除 | 平台会话缺失但曾存在 | 标记删除候选，等待确认 |
| 双方各自追加 | 共同祖先后两端都有新事件 | 建立两个分支，禁止自动拼接 |
| 既有事件被编辑/移除 | 不能证明为纯前缀增长 | 冲突，展示三方差异 |
| 相同 UUID、内容无共同祖先 | ID 被复用或历史被替换 | 阻止同步并要求重新绑定或保留两会话 |
| 格式指纹不受支持 | 适配器不能证明读写安全 | 只读诊断；写入与镜像暂停 |

固定钉选状态保留为平台本地属性，因为 Codex 与 DSH 的语义和入口不同。工作区映射由用户显式配置，不按标题自动迁移。

## 10. 合并与冲突处理

对话不是普通文本文件。系统只自动处理可证明等价的前缀快进和单边元数据变化。

当两个平台都从共同版本继续时，看板显示共同祖先、Codex 分支和 DSH 分支，并提供以下明确操作：

1. **保持两个分支**：不改变任一平台，分别继续。
2. **选择一方作为规范主线**：移动 canonical ref，不覆盖另一平台会话。
3. **基于双方创建延续任务**：建立一个拥有两个父版本的解析版本，以用户填写的合并说明和两条分支的带来源上下文创建新任务。
4. **显式重置目标到某分支**：属于高风险恢复操作，必须预览、确认并具备事务备份；不作为普通“合并”。

解析版本不会声称两条对话在时间上自然连续，也不会伪造工具调用。其 manifest 记录两个父版本、用户选择、合并说明和新平台会话 ID。原来的两个分支和正文对象永久保留，除非用户另行执行经过确认的历史清理。

## 11. 两种 DSH → Codex 路径

### 11.1 默认：创建 Codex 延续任务

用户从 DSH 右键菜单、看板或 Codex 工具卡片选择一个 DSH 版本后：

1. 引擎构建带来源、会话标题、锚点和降格报告的交接上下文；
2. `adapter-codex-continuation` 通过当前 Codex 版本支持的任务创建入口建立新任务；
3. 首条输入明确说明这是从 DSH 延续而来，并携带规范化历史或受大小约束的结构化交接材料；
4. Codex 返回原生 thread ID 后，引擎验证该任务可发现和可恢复；
5. 新任务绑定到同一逻辑会话的新平台分支，不自动启用双向镜像。

该路径不直接写 Codex rollout、索引或 SQLite。若当前 Codex 没有可用的受支持任务创建入口，操作失败并返回可导入的交接包，不得自动切换到原生数据库写入。

交接计划必须在创建前显示预估上下文大小。完整版本超过可用上下文预算时不得静默截断；用户可以改为从某个 checkpoint 起延续，或明确确认“摘要 + 可追溯归档”交接。摘要版本保留原版本 hash 和归档引用，不能冒充完整历史。

### 11.2 可选：原生双向镜像

原生镜像是实验性、逐会话白名单能力。启用前界面必须展示：适配器支持状态、Codex 版本、最近一次契约测试、需要 Codex 停写的原因和恢复能力。

每个镜像映射具有独立状态：

- `active`：适配器兼容，允许计划同步；
- `paused-user`：用户暂停；
- `paused-busy`：Codex 未进入安全停写窗口；
- `paused-incompatible`：版本或格式指纹不受支持；
- `recovery-required`：上次事务未完成，必须先恢复或人工核查。

普通会话继续使用默认延续任务，不会因为安装了原生适配器而获得写权限。

## 12. Codex 原生适配器安全模型

`adapter-codex-native` 按 Codex 版本和存储 schema 建立明确 allowlist。每个支持版本都必须有脱敏 fixture、读取测试、写入候选测试和恢复测试。版本号、关键文件格式、SQLite schema、索引格式或事件类型任一项不匹配时，适配器只报告诊断，不写入。

### 12.1 写入前置条件

- 目标会话已显式启用原生镜像；
- 当前 Codex 版本与格式指纹在 allowlist 中；
- 计划未过期，目标 head 未变化；
- Codex 处于可证明的停写窗口；
- 存储空间足够完成全量备份和候选文件；
- 上一次事务没有未解决 journal。

引擎不强制结束 Codex。无法证明停写时返回 `CODEX_BUSY`，保留计划并提示用户在合适时机重试。

### 12.2 事务步骤

1. 对目标 rollout、状态数据库、开发数据库和会话索引等当前版本实际使用的相关文件建立一致性备份；
2. 把候选 rollout 和索引变化生成到事务 staging 区；
3. 对 JSONL 事件、父子关系、SQLite 完整性和跨文件引用执行离线校验；
4. 使用原子替换或数据库事务发布，逐步写入 journal；
5. 重新通过 Codex 只读适配器确认任务可发现、标题正确、事件可解析且可 resume；
6. 验证失败时按 journal 逆序恢复所有相关文件，并再次执行完整性检查。

不能只回滚单个 rollout 而留下已更新的数据库或索引。恢复成功与否必须作为独立结果展示。

### 12.3 Codex 升级行为

检测到未支持的新 Codex 版本或 schema 后：

- 立即把相关原生镜像置为 `paused-incompatible`；
- 继续允许只读扫描、历史查看和导出；
- 禁止原生写入，也不静默降级为另一种写入方式；
- 默认延续任务只有在受支持的公开创建入口仍可用时继续工作；
- 适配器完成新版本 fixture、测试和用户升级后，镜像从原共同版本重新规划，不补写未经验证期间的猜测结果。

## 13. 事件映射与来源标识

### 13.1 可等价内容

普通 user/assistant 文本、可公开附件引用、标题、时间和分支关系在适配器确认语义等价时映射为目标平台原生事件，并保留来源平台、来源 session ID、来源 event ID 和导入事务 ID。

### 13.2 无法等价的 DSH 事件

DSH 工具调用、工具返回值、内部状态或其他 Codex 无对应语义的事件，不伪装成 Codex 的真实工具执行。它们折叠为一个可展开的 **DSH 导入记录**，包含：

- 原事件类型和来源锚点；
- 对用户可见的摘要；
- 必要的文本结果；
- 明确的 `importedFrom: DSH` provenance；
- 因隐私、大小或格式而省略的字段列表。

私有思维过程不通过推断或界面文本重建。来源没有提供的内容保持不存在。

## 14. 元数据、归档和删除

- **标题**：共同基线后只有一端变化时可按镜像策略同步；两端都变化则人工选择。
- **归档**：原生镜像会话的归档状态可双向自动同步，并生成元数据版本。
- **删除**：永不自动传播。扫描只生成 `deletion-candidate`，界面区分“解除映射”“仅从某平台删除”“从两端删除”。后两者需要逐目标确认和可用备份。
- **钉选**：保持平台本地，不参与同步。
- **工作区**：通过稳定路径/仓库 ID 显式映射；不能仅凭显示名称合并。
- **重命名逻辑会话**：只改变维护系统展示名，不等同于重命名平台会话；用户可另选“同步标题”。

## 15. 用户入口与交互

三个入口只负责提交命令和展示引擎结果，使用同一术语、风险级别和计划 ID。

### 15.1 DSH 会话列表右键菜单

- 在维护看板中打开；
- 立即扫描此会话；
- 创建 Codex 延续任务；
- 启用/暂停原生双向镜像；
- 与 Codex 版本比较；
- 查看版本图；
- 建立命名 checkpoint；
- 解除平台映射；
- 归档；
- 删除（进入独立确认流程）。

DSH 插件可以真实修改 DSH 会话列表和右键菜单，但不包含引擎实现。

### 15.2 独立看板

看板承担完整维护能力，并在视觉、尺寸和操作习惯上与 DSH 及 DSH Maintenance 对齐，而不是另做一套外观：

- 使用 `@linmu/dsh-management-kit/client` 的文档表面、工具栏、页签、搜索框、状态气泡、空状态和确认交互；
- 使用同一组 `--dsm-*` 设计变量、Inter/Segoe UI/Microsoft YaHei 字体、Cascadia Code 等宽信息和 Lucide 图标；
- 沿用 Maintenance 的粘性顶部导航、浅色 surface/soft-surface 工作台、绿色主操作、蓝色链接、黄色警告和红色危险语义；
- 会话详情采用与 Maintenance Generation/Plugin 相同的工作台模板：左侧可缩放 GitGraph 式版本树，右侧按局部页签展示概览、版本内容、三方差异和操作；
- 复用其紧凑按钮、确认对话框、Markdown 渲染、可调分栏和窄窗口响应式规则；
- 不复制 Maintenance 的插件、Generation 或 Host 业务组件，也不调用 Maintenance API。

看板信息架构为：

- **概览**：已登记平台、适配器兼容性、待同步、冲突、暂停镜像和未完成事务；
- **会话列表**：按平台、工作区、模式、状态和更新时间筛选；
- **会话详情**：左侧版本图，中间三方差异，右侧版本说明、平台绑定和可执行操作；
- **同步计划**：展示将新增、更新、归档或删除的对象以及风险级别；
- **事务与恢复**：查看 journal、验证结果、备份和恢复入口；
- **设置**：登记 Codex home、官方 DSH profile、任务创建方式、保留策略和计划任务。

版本图和正文按需加载。进入概览时不读取所有会话的全部事件，也不一次加载每个会话的全部版本说明。

### 15.3 DSH 插件参数面板

参数面板只承载“可调参数”和“直接操作”，不承担 Dashboard 的状态展示职责。

可调参数包括：

- 默认 Codex home 和当前 DSH profile；
- 默认 Codex 工作目录/项目映射；
- 是否同步单边标题变化；
- 是否为已启用镜像的会话自动同步归档；
- 扫描范围和备份保留数量；
- 安全计划是否允许在用户点击同步后批量应用。

操作按钮包括：

- `扫描当前会话`；
- `同步当前会话`；
- `创建 Codex 延续任务`；
- `打开会话维护看板`。

面板只在按钮下方显示本次操作的短反馈，例如“已提交”“需要处理冲突”或错误原因，不显示引擎版本、兼容性卡片、待处理计数、事务列表或长期运行状态。冲突比较、适配器状态、恢复和其他高风险操作全部进入独立看板。

### 15.4 Codex 入口

Codex 端使用官方插件能力提供 Skill、MCP 工具和工具卡片，例如：

- 查看当前任务的 DSH 映射；
- 把当前 Codex 任务导入/同步到 DSH；
- 从指定 DSH 会话创建新的 Codex 延续任务；
- 查看镜像状态、冲突和暂停原因；
- 打开独立看板中的对应逻辑会话。

当前插件接口没有可靠的 Codex 原生侧边栏右键扩展点，因此不注入 Codex 会话列表。所有高风险原生镜像操作在工具卡片中展示计划后，仍由独立看板完成确认。

## 16. 失败处理与恢复

- 所有写事务在开始前创建事务目录和可验证备份。
- journal 每完成一步立即落盘；引擎重启后能够判断继续验证还是恢复。
- 平台验证失败时，事务状态不是简单的 `failed`，而是 `restored`、`restore-failed` 或 `manual-review`。
- 任何无法确定的平台状态都禁止继续堆叠新写入。
- checkpoint 是用户命名的跨平台恢复点；普通自动版本不是 checkpoint。
- 恢复 checkpoint 会生成新计划并移动/恢复平台状态，不删除 checkpoint 之后的版本图。
- 日志使用错误码，例如 `CODEX_BUSY`、`ADAPTER_INCOMPATIBLE`、`PLAN_STALE`、`UNSTABLE_READ`、`DIVERGED` 和 `RECOVERY_REQUIRED`，界面同时显示非技术说明。

## 17. 干净启动与现有会话发现

新项目不读取旧插件 ledger、不加载旧同步脚本，也不保留 `/codex-sync` 兼容命令。首次启动直接扫描用户登记的 Codex home 与官方 DSH profile，为现有平台会话建立新版本库基线。

首次发现必须幂等，并按以下可信度匹配逻辑会话：

1. 优先使用平台会话中已有的稳定来源 UUID、provenance 和显式跨平台绑定；
2. 没有显式绑定时，使用规范化根事件 hash、稳定工作区 ID 和可证明的内容前缀关系提出匹配候选；
3. 标题只用于帮助用户识别，不能单独作为自动合并依据；
4. 同一 UUID 对应多个内容不兼容的会话时保留为独立候选并阻止自动同步；
5. 用户确认候选后才建立 PlatformBinding；未确认会话仍可作为单平台 LogicalSession 管理；
6. 重复扫描相同平台状态不得创建重复 LogicalSession、PlatformBinding 或 SessionVersion。

新系统验收完成后直接从官方 DSH profile 卸载 `dsh-codex-session-sync`，再安装新的 `dsh-session-maintenance` 插件。旧插件目录和旧 ledger 可以在用户确认新基线完整后删除；它们不会进入新项目的数据路径、运行依赖或恢复链。

## 18. 性能设计

- SQLite 使用 WAL 和明确 schema migration；正文对象按 hash 去重并压缩。
- 初次列表只加载会话元数据、head、计数和状态；正文、diff 和历史图分页按需读取。
- 对每个平台保存扫描游标、mtime/size、事件数和前缀摘要，只有变化候选才重新计算完整 hash。
- 大会话按事件块建立摘要，前缀比较不需要重复解码全部历史。
- 读取线程有界并发；同一平台根目录写入严格串行。
- 看板通过作业事件流获取进度，不高频轮询完整账本。
- 保留策略按事务数量、总大小和 checkpoint 引用清理；被 checkpoint 或未解决冲突引用的对象不能回收。

## 19. 测试策略

### 19.1 单元与属性测试

- 规范化和稳定 hash；
- 前缀、祖先、分叉和两父版本图；
- 标题/归档元数据冲突；
- 删除候选与解除映射；
- 内容对象去重和垃圾回收保护；
- 计划指纹过期与幂等 apply。

### 19.2 适配器契约测试

- 每个受支持 Codex 版本使用脱敏 fixture 验证扫描、候选写入和恢复；
- 官方 DSH 各受支持版本/profile 使用临时 home 验证读写、workspace/projection 和分支；
- 未知字段、截断 JSONL、损坏 SQLite、被占用文件和升级后的 schema 必须安全失败；
- DSH 工具事件到“DSH 导入记录”的映射不得被识别为原生 Codex 工具执行。

### 19.3 集成与故障注入

- 在不读取旧 ledger 的情况下连续执行两次干净发现，不重复创建逻辑会话、绑定或版本；
- Codex → DSH 快进、DSH → Codex 延续任务和归档双向同步；
- 双方追加后保持两个分支并生成可审查合并计划；
- 在备份、候选生成、数据库提交、索引替换和验证每一步注入失败，确认完整恢复；
- 引擎、DSH 或看板中途退出后，可从 journal 恢复；
- 所有测试使用临时 Codex/DSH home，默认测试命令不得读取或写入真实会话。

### 19.4 界面契约测试

- DSH 右键菜单和参数面板提交的操作与看板使用同一计划语义，短反馈中的计划 ID 可在看板准确打开；
- Codex 工具卡片不能绕过引擎确认；
- 大量会话时首屏只请求摘要，不加载正文；
- 不兼容、忙碌、冲突和恢复失败都有明确可操作提示。

## 20. 实施分解

设计按以下顺序进入实施计划，后续每一阶段都先完成 CLI/引擎能力，再补同一能力的 GUI：

### 阶段一：独立只读内核

- 建立新 monorepo、domain、store、CLI 和 loopback API；
- 实现 Codex/DSH 只读适配器、规范化、内容对象和版本图；
- 实现不依赖旧 ledger 的干净发现，并提供 scan、diff、plan 和 dry-run；
- 用现有真实数据的脱敏副本验证不重复映射。

### 阶段二：DSH 安全写入与界面

- 实现 DSH 事务写入、验证和恢复；
- 实现全新的 `dsh-session-maintenance` 插件并卸载旧同步插件；
- 使用 DSH Management UI 契约实现独立看板、DSH 右键菜单和轻量参数/操作面板；
- 验收 Codex → DSH 安全快进与分叉保留。

### 阶段三：Codex 延续任务

- 实现受支持的 Codex 新任务创建适配器；
- 建立交接上下文、来源标识、任务验证和平台分支绑定；
- 提供 Codex Skill/MCP 工具卡片；
- 验收新任务可在 Codex 中原生显示、恢复和继续。

### 阶段四：受控原生镜像

- 为明确的 Codex 版本建立原生适配器 fixture 与 allowlist；
- 实现停写检测、全事务备份、候选校验、原子发布和完整回滚；
- 实现逐会话白名单、自动暂停和手动冲突解析；
- 经过独立测试后再向正式 Codex home 开放，不与前三阶段同时抢跑。

每个阶段使用独立实施计划和验收记录。阶段四失败或暂缓不影响前三阶段作为完整可用产品发布。

## 21. 验收标准

系统达到首个稳定版本时必须满足：

- 同一批现有会话连续扫描两次不会产生重复逻辑会话或重复版本；
- 修改一端后能建立新版本，并正确识别未变化、前缀增长和分叉；
- Codex → DSH 安全同步保留 DSH 独立分支；
- DSH 会话可创建新的、原生显示且能继续的 Codex 任务；
- 原生镜像只对已确认白名单会话启用；
- Codex 版本不兼容或忙碌时零写入并显示明确暂停原因；
- 双方分叉不会被自动拼接或覆盖；
- 归档可按策略双向同步，删除始终要求确认；
- 任一写入步骤失败均有可验证恢复结果；
- DSH 停止或重启不影响引擎账本、看板和恢复任务；
- EAC 未安装时全部核心功能仍可工作；
- DSH、独立看板和 Codex 入口使用同一版本图、计划和事务记录。

## 22. 已确认的产品决策

1. 会话维护能力由全新独立项目实现，不保留旧同步插件的运行兼容层。
2. 默认反向迁移是“创建新的可持续 Codex 任务”。
3. 少数重要会话可以显式启用原生双向镜像，并在 Codex 中显示为原生历史。
4. Codex 是主力 harness，原生写入必须保守、可暂停、可回滚。
5. Codex 格式不兼容时暂停镜像，不静默降级、不猜测格式。
6. 无法等价转换的 DSH 工具事件折叠为带来源标识的导入记录。
7. 归档状态允许双向自动同步，删除永远要求确认。
8. DSH 端提供真实会话右键菜单；Codex 端使用官方工具卡片/Skill，不修改原生侧边栏。
9. 会话版本自动记录，重要版本由用户添加标签或 checkpoint。
10. 双方对话分叉需要人工解析；只有安全前缀增长可以自动快进。
11. 引擎独立运行，三个界面入口共享同一 API、账本和事务链。
12. 独立 Dashboard 与 DSH Maintenance 使用同一 UI 契约和风格，但不依赖 Maintenance 服务运行。
13. DSH 参数面板只提供可调参数、操作按钮和本次操作短反馈；完整状态统一进入 Dashboard。
14. 新系统验收后卸载 `dsh-codex-session-sync`，不迁移其命令、配置或 ledger。
